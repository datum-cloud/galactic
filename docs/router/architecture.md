# Tenant router architecture

This page describes the component boundaries and invariants. Use [configuration](configuration.md) for settings and [the documentation index](../README.md) for deployment and development guides.

## Overview

`galactic-router` watches BGP CRDs directly via controller-runtime — no gRPC
sidecar, no provider CRD lifecycle. When `galactic-veth`/`galactic-tap`
attaches a pod/VM and `galactic-bgp` writes a `BGPAdvertisement` CRD (see
[ARCHITECTURE-CNI.md](../cni/architecture.md)), `galactic-router` reconciles
that CRD and injects the EVPN path into the node-local GoBGP server. GoBGP
distributes the path to a BGP route reflector, enabling pods/VMs on
different nodes or clusters to reach each other via SRv6-encapsulated
traffic.

### SRv6 SID encoding (control-plane side)

`galactic-router`'s own reconciler derives the SID value for the BGP
control-plane side: advertising it in a BGP Prefix-SID path attribute (RFC
9252 SRv6 L3 Service TLV, `internal/runtime/gobgp/paths.go`'s
`prefixSIDAttr`) — not the EVPN Type 5 route's own Gateway IP field, which
RFC 9136 requires to share the prefix's own address family and so cannot
carry an IPv6 SID for an IPv4 VPC prefix. This SID is computed via
`srv6.ComputeSID` (`internal/plumbing/srv6/usid.go`, called from
`internal/reconcile/reconcile.go`) from the same inputs
(`BGPRouter.spec.srv6Locator` + `nodeID` + the attachment's VRFID) that
`galactic-bgp`'s `registerEBPFDatapath` independently derives for the CNI
side's eBPF datapath registration — see
[ARCHITECTURE-CNI.md#srv6-sid-encoding](../cni/architecture.md#srv6-sid-encoding).
The CNI side and the router side compute the same bit layout via separate
code paths (`uformat` is the single source of truth both build on), by
design — see `internal/plumbing/ebpf/doc.go`.

All nodes in the same VPC derive the same BGP Route Target by truncating the
48-bit hex VPC identifier to its low 32 bits (`uint32(v)`), formatted as
`ASN:NN`, enabling automatic cross-node path import without explicit RT
configuration. The RT is also used as the `BGPVRFInstance`'s Route
Distinguisher and import/export Route Target.

## Entry Points

### `cmd/galactic-router/main.go` / `root.go` — Router daemon

`main.go` is a 3-line wrapper around `newRootCommand().Execute()`; all startup logic
lives in `root.go`'s `runCmd`:

1. Validate config (`--node-name` required). Env vars: `GALACTIC_ROUTER_NODE_NAME`,
   plus optional `GALACTIC_ROUTER_BGP_LISTEN_PORT`,
   `GALACTIC_ROUTER_BGP_LOCAL_ADDRESS`, `GALACTIC_ROUTER_METRICS_PORT`,
   `GALACTIC_ROUTER_GRPC_HEALTH_PORT`, `GALACTIC_ROUTER_GC_NAMESPACE`,
   `GALACTIC_ROUTER_GC_INTERVAL`, `GALACTIC_ROUTER_REFLECTOR`.
2. Resolve the BGP local address (`resolveBGPLocalAddress`): the explicit
   env var if set, otherwise auto-detected from the host's `lo` interface.
3. Build controller-runtime manager (metrics on configurable port, default
   `:9179`; no HTTP health endpoint).
4. Start gRPC health server on a configurable port (default `:5179`).
5. RBAC pre-flight: `checkWatchPermissions` (in `main.go`) issues a
   `SelfSubjectAccessReview` for every watched resource type and logs an actionable
   error if watch RBAC is missing (informer caches would otherwise silently never sync).
6. Open this node's own `vip_xlat_table` handle (`controller.PinnedVIPTranslationTable`
   over `vipxlatmap.OpenPinnedVipXlatTable`) for `ServiceVIPBindingReconciler`
   and the GC ticker's `vip_xlat_table` sweep. A missing pin (no eBPF uSID
   datapath loaded on this node yet) is logged, not fatal. Each binding
   reconcile and each sweep tick retries the open until it succeeds, so on a
   node that has just booted, where `galactic-router` can start before
   `galactic-cni` pins the map, bindings bind once the pin appears without a
   restart. A route reflector never runs `galactic-cni`, so the pin never
   exists there and the reflector logs its absence at Info rather than as an
   error. Once open, the handle is kept. When a `galactic-cni` upgrade changes
   the map's layout, `attach.Load` unpins and recreates the map, and this
   process keeps writing to the old one until it restarts, so restart
   `galactic-router` after `galactic-cni` has rolled out such a change.
7. Register field indexes: BGPPeer→secret, BGPPeer→router, BGPPolicy→router,
   BGPAdvertisement→router, BGPVRFInstance→router, BGPRouter→node,
   VPCAttachment→`status.vpc`.
8. Register the peer-state event emitter (`controller.NewPeerStateEventEmitter`)
   with the manager — see the peer-FSM design decision below.
9. Register the controllers: BGPRouter, BGPPeer, BGPAdvertisement,
    BGPVRFInstance, BGPPolicy, Secret, Node, ServiceVIPBinding,
    NetworkServiceBinding, NodeDeparture, ServiceRoutePolicy and
    ServiceProducerHealth (plain role only; a route reflector has no service
    route maps to program and skips both),
    and GC (the GC controller also starts a ticker goroutine that waits for
    cache sync, then runs on `--gc-interval`, default 5m; NodeDeparture
    sweeps on the same interval, and when `vip_xlat_table` opened in step 6,
    each GC tick after the first pass also sweeps it).
10. `mgr.Start(ctx)` — blocks until the signal-handler context is cancelled.

Apart from the ServiceRoutePolicy and ServiceProducerHealth controllers and the `vip_xlat_table` log
level noted above, this is identical whether the pod is running in the plain
role (`config/galactic-router/overlays/router/`, opt-in via
`galactic.datumapis.com/galactic=router` — deployed on both `compute` and
`edge` nodes) or the route-reflector role (`config/galactic-router/overlays/control/`,
`galactic.datumapis.com/galactic=control`) — `galactic-router` carries no
gateway-role code path of its own at all, and runs as its own independent
DaemonSet on `edge` nodes rather than co-located inside `galactic-gateway`'s
pod; see [ARCHITECTURE-GATEWAY.md](../gateway/architecture.md) for what runs
there instead.

## Key Design Decisions

- **GoBGP embedded, lazy-started.** GoBGP runs in-process and starts only when the first `BGPRouter` is reconciled for that router; `Apply` re-runs on every subsequent reconcile too (subject to hash-based no-op suppression), re-applying peers/VRFs/EVPN/policies each time. `listenPort` defaults to `179`; `-1` (outbound-only) is an operator choice for specific deployments, not the codebase default. ASN, RouterID, or `listenPort` changes each trigger a full `Reconfigure` (fresh `BgpServer` — `StopBgp` is not called because it permanently terminates the v4 Serve loop).
- **`BGPRouter.spec.listenPort` overrides the process-wide default per router.** `GALACTIC_ROUTER_BGP_LISTEN_PORT` (via `NewRuntimeFactory`) sets the fallback every `GoBGPRuntime` on this node starts with; `internal/reconcile/reconcile.go` carries `spec.listenPort` into `DesiredRouter.ListenPort`, and `internal/runtime/gobgp/runtime.go`'s `applyGlobal` uses it in place of the fallback when set — the same override pattern `BGPPeer.spec.remotePort` uses over its `1790` default. This lets one router accept inbound BGP without switching its node to the `rr` role.
- **Overlay BGP port.** galactic-router peers connect outbound on port `1790` by default (configurable per-peer via `BGPPeer.spec.remotePort`). Port `179` is occupied by the underlay FRR `bgpd` on every node, so the overlay uses a non-conflicting port. The `BGPPeer` CRD defaults `remotePort` to `179` (the IANA BGP port); galactic-router overrides this to `1790` when the field is unset, so existing CRDs without an explicit value continue to work. Set `remotePort: 179` explicitly when peering with external BGP speakers that listen on the standard port.
- **VRF/route-target model via BGPVRFInstance.** `galactic-bgp` (the CNI chain, see [ARCHITECTURE-CNI.md](../cni/architecture.md)) creates a `BGPVRFInstance` (RouteDistinguisher + import/export Route Targets, all set to the derived RT) before the `BGPAdvertisement`; `galactic-router`'s GoBGP runtime applies VRFs (`applyVRFs`) before originating EVPN paths (`applyEVPN`). `galactic-gateway`'s own `BGPAdvertisement`s (VIP/self-address routes, see [ARCHITECTURE-GATEWAY.md](../gateway/architecture.md)) leave VRFID/Function unset entirely — they carry no SRv6 decap behavior of their own.
- **CRD-driven config, no sidecar gRPC.** `galactic-router` watches BGP CRDs directly via controller-runtime. `galactic-bgp` writes `BGPVRFInstance`/`BGPAdvertisement` CRDs; the router reconciler picks them up. No in-node gRPC calls between any of the CNI-chain binaries and `galactic-router`.
- **Hash-based no-op suppression.** SHA-256 over the sorted `DesiredRouter` prevents redundant GoBGP Apply calls on every CRD event. A matching hash skips Apply only when the runtime is healthy, holds every desired peer, and reports every desired VRF `Applied`; see the VRF wiring note below.
- **RuntimeFactory pattern.** `galactic-router` always builds a `gobgp.NewRuntimeFactory(...)` at startup — GoBGP is the only backend. A `RuntimeFactory` is a plain function value (`func(types.NamespacedName) (RouterRuntime, error)`), so a future backend still only needs a new factory function and a call-site change here, not a controller change.
- **DEL is intentionally minimal everywhere in the CNI chain; GC reclaims shared state asynchronously.** See [ARCHITECTURE-CNI.md](../cni/architecture.md#key-design-decisions) for the CNI-side half of this decision. `galactic-router`'s GC controller (ticker-driven, default every 5m) reclaims orphaned CRDs, stale kernel VRFs, and stale eBPF entries once no live container still references them. A Galactic Edge attachment counts as a reference too: GC keeps the VRF and `BGPVRFInstance` of a VPC an edge attachment uses on the node and deletes them only under that VPC's write fence, shared with `galactic-edge` through the `/var/lib/galactic-edge/ownership` mount (`internal/edge/maintenance`, see [gc-cmd-sequence.md](../cni/gc-cmd-sequence.md)).
- **gRPC health, configurable port.** Liveness and readiness probes use the gRPC health protocol (`google.golang.org/grpc/health`) on a configurable port (default `5179`). No HTTP health endpoint. `galactic-gateway` follows the identical convention on its own port — see [ARCHITECTURE-GATEWAY.md](../gateway/architecture.md).
- **A Galactic Edge route is advertised only while its node forwards it.** `galactic-controller` publishes one `BGPAdvertisement` per accepted edge route, labeled `galactic.datumapis.com/edge-route` and naming the holder's host link and address (`internal/edge/route/publish.go`). `BuildDesiredRouter` leaves such an advertisement out unless the node's pinned forwarding gate holds an unexpired gate for exactly its prefix on that link, read on every build (`reconcile.EdgeGate`, `cmd/galactic-router/edgegate.go`), and `edgeGateWatch` polls the gates of this node's edge advertisements every 250 ms to wake the router when one opens or closes, so a gate deadline withdraws the prefix with no API event. Without the pinned gate map the router advertises no edge route; it opens the map again at most every second while it is missing or after a read fails, so a router started before the uSID datapath needs no restart. A route reflector checks no gate and advertises none. A left-out advertisement is reported `Advertised` False with reason `GateClosed`. See the [provider contract](../edge/provider-contract.md#publication).

- **`galactic-router` carries no gateway-role code.** The edge XDP load-balancing gateway used to be a `galactic-router` mode; it was split into its own `galactic-gateway` binary specifically so a crash on either side no longer takes the other down with it — see [ARCHITECTURE-GATEWAY.md](../gateway/architecture.md) for the full rationale and design.
- **Peer FSM transitions are logged by a dedicated GoBGP event watcher, which also drives real-time BGPPeer Kubernetes Events.** GoBGP's own logger writes through the process's `slog` default under logger `gobgp` (`internal/runtime/gobgp/server.go`'s `buildServerOptions`), at the binary's `--log-level`. On top of it, `internal/runtime/gobgp/peer_monitor.go` runs a shared `BgpServer.WatchEvent(..., WatchPeer())` goroutine (the same one-goroutine-per-runtime pattern `monitor.go`'s `watchEVPNRIB` uses for EVPN best-path) that diffs each peer's FSM state against `lastPeerState` and logs a `slog.Info` line on every real transition, including `disconnectReason`/`disconnectMessage` when a peer drops out of Established. The same transition is also handed to an optional `model.PeerStateObserver` (set via `gobgp.NewRuntimeFactory`'s `observer` parameter): in production this is `internal/controller/peer_events.go`'s `PeerStateEventEmitter`, a `manager.Runnable` that resolves the peer's address to its `BGPPeer` object and raises a `SessionEstablished`/`SessionDown` Kubernetes Event on it — but only for transitions into/out of Established, not every intermediate FSM hop (see the emitter's own doc comments for why). This is independent of, and does not replace, the periodic (`peerStatusRequeue`, 30s) `BGPPeer.Status` update in `internal/controller/bgprouter_controller.go`'s `updatePeerStatuses`: that keeps the CRD's status current on a poll and can miss a transition that reverts between two polls; the `slog` line and the Event are both real-time and don't have that gap. See `docs/plans/router-bgp-peer-session-events.md` for the full design.
- **Routes for route-target-less EVPN paths defer to the underlay.** A path with no route target (the gateway's anycast VIPs, and each egress shard's SID `/64` and masquerade address) becomes a plain kernel route toward its BGP next hop, with no encapsulation. These routes live in their own table, `srv6.PlainRouteTable` (`0xFFFE0000`), marked `proto 250`, and are reached through two policy rules ahead of the main table's own: `32000: lookup main suppress_prefixlength 0`, then `32001: lookup 0xFFFE0000`. An underlay route for the same destination, or for anything more specific than the default route, therefore always wins. Keeping them out of the main table is required, not cosmetic: zebra imports every main-table route it did not install as a `kernel` route with distance 0, so a plain route there stopped FRR installing its own BGP route for the same prefix (#670). The kernel cannot resolve an IPv6 next hop recursively, so each route is written with the link and next hop the gateway resolves to at the time. `internal/runtime/gobgp/plainroutes.go` re-resolves every route whenever the main table changes and every 30s, and retries one that cannot resolve yet. It removes owned routes no path asks for once a two-minute startup grace has passed, and deletes the unmarked main-table route an earlier version left for each prefix. `ip route show table all proto 250` lists every route it owns. XDP datapaths that call `bpf_fib_lookup` with `BPF_FIB_LOOKUP_DIRECT` (`natprog`, `edgeprog`) read the main table only and do not see these routes.
- **A tenant VRF route that fails to install is retried, not dropped.** `processEVPNPath` writes a VRF-scoped path's route into `egress_route_table` through `internal/runtime/gobgp/vrfroutes.go`. `Register` resolves the SID's uplink and neighbor MAC at write time, which fails while an uplink is still coming up after a restart, and BGP never redelivers an unchanged best path, so before #676 such a route stayed missing until the path changed upstream. `vrfRoutes` keeps each failed route in a pending set and retries it whenever the main table changes (1s debounce) and every 30s, until it installs or its path is withdrawn; removing a VRF drops its pending routes. One mutex serializes every write to the map from this runtime, taken per route during a retry so an unresolvable neighbor (up to 2s) does not hold up the RIB watcher for the whole pass. `EgressRouteTable.Refresh` cannot cover this: it walks existing entries only. The pending count, and the plain-route reconciler's failing count, are exported as `galactic_router_route_install_failing{kind="vrf"|"plain"}`, and `GalacticRouterRoutesNotInstalled` fires when either stays above 0 for 10 minutes.
- **`ServiceVIPBinding`s are generated, one per node per backend.** `NetworkServiceBindingReconciler` (`internal/controller/networkservice_binding_controller.go`) runs on every node and writes a binding for each VIP of each accepted `NetworkService`, at most one per family (`ruleTranslatedVIPs`) and, for the IPv4 VIP, only while some gateway node's `<node>/IPv4Served` condition reports it loaded (`ipv4LoadedOnSomeNode`; a status change to that signal passes `ruleBindingInputsChanged`, and the node deletes its IPv4 bindings once no gateway does), and each backend the rule's `backendSelector` places on this node, through the same `selectRuleBackends` the gateway uses, so the gateway never sends a backend's flows to a node with no binding planned for it. Workloads are IPv6 only, so both VIPs' backends are the selected attachments' IPv6 addresses: an IPv4 VIP's binding pairs the IPv4 `vipAddress` with an IPv6 `backendAddress`, which the backend node serves by translating the flows (see [ARCHITECTURE-CNI.md](../cni/architecture.md#key-design-decisions)). `ServiceVIPBindingReconciler` refuses an IPv4 `backendAddress` with `BindFailed`. Each node writes and deletes only its own bindings (labelled `galactic.datum.net/binding-node` and `app.kubernetes.io/managed-by: galactic-router`), so there is one writer per object and no leader election. A binding is owned by its rule, records the rule's `vpcRef` (which names the VRF its rows go in) and takes `egressKind` from the attachment's interface mode. `ServiceVIPBindingReconciler` programs a binding only when a `BGPAdvertisement` on this node's `BGPRouter` with that VRF's ID has a prefix containing `backendAddress`, and otherwise reports `BindFailed`; it watches advertisements on its own router so a binding written before its advertisement converges, and teardown skips the check. A backend serves only the oldest rule (by creation time, then namespace/name) selecting it on the same backend port and protocol, since its node translates the backend's replies back to only one VIP; a claim (`backendClaim`) carries the VIP's family, since a reply to an IPv4 client takes the IPv4 VIP's egress-translated row and any other reply the IPv6 VIP's egress row, so one backend socket answers for one VIP of each family, an IPv4 rule never competes with an IPv6 one, and two rules with IPv4 VIPs on one socket do; both sides compute that owner with `ruleBackendOwners` over every rule in the namespace, so a newer rule gets no binding for the backend and no flows for it from the gateway, and every rule in a namespace is re-queued when one of them changes. Rules compete only within a VPC, so the per-VPC `VPCAttachment` fan-out still reaches every rule an attachment change can affect. The node summarizes its bindings on the rule as `<node>/BackendsBound` (`BackendsClaimed` names a backend an older rule serves); a rule whose spec cannot be built into bindings (a second IPv6 VIP, or a selector that does not parse) keeps the node's existing bindings, the same as a rule that loses `Accepted`, so an invalid edit does not drop the backend nodes' `vip_xlat_table` rows; a second IPv4 VIP does the same for the IPv4 family alone, writing no IPv4 binding and keeping the IPv4 ones it had while the IPv6 VIP's bindings stay current, and both report `InvalidRule`. Only the nodes that hold bindings for such a rule report `InvalidRule`, since the gateways already report the error and a condition from every node would be a status write per node per edit. Each rule reconcile lists only its own VPC's attachments, through the VPCAttachment→`status.vpc` field index (`listVPCAttachmentsInVPC`), and skips the cache's deep copy because nothing it does writes to them. Several backends of one VIP can share a node: the gateway writes each backend's slot into the uSID and `usid.c` keys the ingress row on it (#799).
- **Each node probes its own backends and publishes their health.** For a `NetworkService` with `spec.healthCheck`, `BackendHealthReconciler` (`internal/controller/backendhealth_controller.go`) runs one TCP probe loop per backend on its node (`internal/healthprobe`), over the backend's host-side interface (the attachment's `status.hostInterface`) from that interface's link-local address, on `healthCheck.port` or the rule's `backendPort`. The link-local source is what lets the SYN-ACK back: `usid_egress` hands a reply to a link-local destination to the kernel before its VIP rewrite (see [ARCHITECTURE-CNI.md](../cni/architecture.md#key-design-decisions)). A decision moves after `unhealthyThreshold` consecutive failures or `healthyThreshold` consecutive successes; a probe that cannot be sent (no interface, no link-local address) counts toward `Unknown`/`ProbeUnavailable`, never toward `Unhealthy`. The decision goes into `status.health` of each of the backend's bindings, with the attachment UID and probed port, by a merge patch of that field alone and only when it changes, so it never races the `Bound` condition. Every binding of one backend shares one loop. A restarted router seeds each loop from the published decision when its attachment UID and port still match, so a restart changes no gateway's table. A rule losing its `healthCheck` clears `status.health` and stops the loops. The design is [docs/gateway/backend-health.md](../gateway/backend-health.md).
- **A `Spread` service endpoint's producers are probed by their own node, and a consumer's route reads a producer set.** `ServiceProducerHealthReconciler` (`internal/controller/serviceproducerhealth_controller.go`) runs one `internal/healthprobe` loop per producer on its node of each `ServiceEndpoint` with `spec.distribution: Spread`, to the producer attachment's first IPv6 address on `healthCheck.port`, and server-side applies that node's `ServiceEndpointProducerReport` for the endpoint (at most 16 entries, owned by the endpoint) under its own field manager (`galactic-router/<node>`), so no object grows with the number of nodes. It deletes its report when it has no producers left, deletes reports of other nodes not renewed for 10 minutes, and removes its own entries from the endpoint's `status.producers`, where routers that predate reports write. Each node renews its entries every 15 seconds (`renewTime`); an entry not renewed for 60 seconds is expired, drains nothing, and ranks a remote producer after every currently reported one (`serviceroute.ProducerReportCurrent`). `ServiceRoutePolicyReconciler` requeues for the next expiry and ignores report and endpoint updates that only renew current entries. `ServiceRoutePolicyReconciler` reads them, through `serviceroute.WithProducerReports`, which keeps, for each producer and node, the more recently renewed of its report entry and its `status.producers` entry: for a Spread endpoint, `serviceroute.Compile` emits one `LocalSet` intent per consumer holding every producer on the consumer's node, `Unhealthy` ones marked draining unless all are. `EBPFRouteProgrammer` writes it as a mode-3 `service_route_table` row plus a `service_producer_set_table` row under the same key; `usid_egress` pins each TCP flow in `service_flow_table` and picks a producer per UDP datagram (see [docs/router/private-service-routes.md](../private-services/README.md#several-producers-on-one-node)). A changed `LocalSet` intent is applied before the old one is removed, and the programmer keeps the newest of a key's producer sets in the map, so a health or membership change never drops the consumer's route. A datapath without the producer set map gets `serviceroute.ErrProducerSetsUnavailable` for `LocalSet` intents only.
- **Surviving routers clean up after a departed node.** Only a node's own `NetworkServiceBindingReconciler` clears its `<node>/BackendsBound` conditions and deletes its generated bindings, and only its own `ServiceVIPBindingReconciler` removes the teardown finalizer from bindings targeting it. So once a node's `Node` object is deleted, `NodeDepartureReconciler` (`internal/controller/node_departure_controller.go`) on every other router removes that node's `BackendsBound` condition from every `NetworkService`, deletes its generated bindings and removes the finalizer from every binding whose `targetRef.name` names it, hand-written ones included; the kernel rows went with the node. Without it the conditions stayed forever and a deleted rule's bindings stayed `Terminating`. Every Node create and delete maps to one sweep key, so the sweep runs on the initial Node list (startup), on every Node delete and every `--gc-interval`, and a router down during the delete still converges. A node missing from the cached Node list counts as departed only once an uncached `Get` returns NotFound. Every router sweeps, with no leader election: status writes and finalizer patches retry on conflict (the patch carries the resourceVersion) and NotFound counts as done.
- **Deleting a `ServiceVIPBinding` does not need its VRF on the node.** A binding's two `vip_xlat_table` rows are keyed on its VRF's uSID Argument. `ServiceVIPBindingReconciler` reads it from the `BGPVRFInstance` its `vpcRef` names on this node, and that is gone once the VPC leaves the node. Before #750, deletion re-derived it, failed, held the finalizer forever and left both rows in the map. Teardown now finds the rows by value with `vipxlatmap.UnregisterBinding`: since #764 each key carries the VIP or backend address, and since #799 the ingress key also carries the backend's slot, so the binding's ingress row (its VIP, port and slot, rewriting to its backend) and egress row (its backend and port, rewriting to its VIP) are found exactly, under any Argument. Each row is removed only while it still holds the binding's values, so a row another binding has since written stays. When the VRF context still resolves, `UnregisterBindingAt` applies the same checks at that location too. Neither pass deletes a row without first reading it, and a process-wide lock keeps a bind from landing between the read and the delete. A value check cannot tell two bindings with identical values apart, so while such a twin is live on the node, deleting one removes nothing. Rows exist only for an IPv6 backend, so an IPv4 or unparseable `backendAddress` skips both passes instead of blocking deletion. Only a failed kernel delete keeps the finalizer. Rows left behind some other way, by a finalizer cleared by hand, a crash or a manual write, are removed by the periodic sweep below; to remove one sooner, use `galactic-router vip xlat list` and `vip xlat remove --protocol --vip --port --backend --backend-port` (`--slot` defaults to the backend's own), run in that node's `galactic-router` pod (`kubectl exec <pod> -- /galactic-router vip xlat list`).
- **`vip_xlat_table` holds both VIP families in one layout.** The map (`struct vip_xlat_key`, 32 bytes: block, argument, protocol, direction, port, slot, 16-byte address; `struct vip_xlat_value`, 18 bytes: 16-byte address, port) is pinned by `galactic-cni` at `/sys/fs/bpf/galactic/vip_xlat_table` and reused across restarts and upgrades by `attach.Load`; `galactic-router`'s `ServiceVIPBindingReconciler` and the `vip xlat` CLI are its only writers. Its layout is fixed, since CNI ADD and binding time write the rows and a new layout would empty the map until every binding was written again. A binding writes two rows, by its VIP's family (every key also carries block, argument and protocol):

  | VIP  | Direction               | Key: slot, address, port         | Value: address, port  |
  | ---- | ----------------------- | -------------------------------- | --------------------- |
  | IPv6 | ingress (0)             | backend slot, VIP, VIP port      | backend, backend port |
  | IPv6 | egress (1)              | 0, backend, backend port         | VIP, VIP port         |
  | IPv4 | ingress (0)             | backend slot, `::ffff:VIP`, port | backend, backend port |
  | IPv4 | egress-translated (2)   | 0, backend, backend port         | `::ffff:VIP`, port    |

  The backend is always IPv6. An IPv4 VIP is stored IPv4-mapped, the form `usid.c` builds from an IPv4 header. `vipxlatmap` takes an IPv4 VIP only as a 4-byte `net.IP`, refuses a 16-byte IPv4-mapped one and an IPv4 backend, and reads the VIP back unmapped. `vipxlatmap.Key` carries the direction, so a live IPv6 VIP's egress row never keeps a stale egress-translated row on the same socket through the sweep. The datapath's IPv6 lookups skip an IPv4-mapped address, so an IPv6 packet never takes an IPv4 VIP's row. An IPv4 VIP's rows exist only while a gateway reports the rule's IPv4 VIP loaded, so turning `GALACTIC_GATEWAY_IPV4_VIPS` off on every gateway deletes its bindings and, through their finalizers, the rows. A release before translation ignores the rows that remain across a rollback: its datapath looks up no egress-translated row and either looks up no IPv4 packet or ignores an IPv4 row with an IPv6 value. Its router can delete neither of an IPv4 VIP's rows: its `vipxlatmap` refuses the ingress row's IPv4-mapped key, and its sweep counts an error for that row on every pass, and it does not know the egress-translated row's direction, so its sweep never removes that one. So remove both with this release's `vip xlat remove` before rolling back. Rows a router with the native IPv4 path wrote, an IPv4 VIP rewritten to an IPv4 backend with both addresses IPv4-mapped, are claimed by no binding in this release, which refuses an IPv4 `backendAddress` and deletes such generated bindings, so the sweep removes them (`TestVIPXlatSweeper_RemovesIPv4BackendRows`), and until then the datapath drops their traffic as `vip_ipv4_backend`; see [configuration.md](../gateway/configuration.md#rolling-out-and-rolling-back-ipv4-vips).
- **`vip_xlat_table` is swept on the GC ticker.** `controller.VIPXlatSweeper` (`internal/controller/vipxlat_sweep.go`) runs on every GC tick after the first, never in the initial pass at startup, so the `ServiceVIPBinding` reconciler has re-registered every live binding first. It takes the table's generation, lists every `ServiceVIPBinding` targeting this node (including ones being deleted, whose finalizer owns their rows), resolves each one's two rows the way the reconciler does, and calls `VipXlatTable.Reconcile`, which removes every row not in that set unless it was registered after the snapshot. The live set is by key, so a row is kept whatever value it holds. A binding whose VRF context does not resolve right now has no known Argument, so every row shaped like one of its rows (direction, slot, protocol, address and port, under any Block and Argument) is kept instead. A binding whose spec does not parse never wrote a row and protects nothing, and any error listing bindings or building the index skips the whole pass. This is what removes the slot-0 ingress rows a router built before #799 wrote: the current key carries the backend's slot, so nothing else ever matches them. `usid.c` has no slot-0 fallback, so `galactic-gateway` and `galactic-router` have to be upgraded together across #799; a node whose router has not yet rewritten its rows with slots drops the flows a new gateway sends it.

## Known Constraints

- **GoBGP RIB is ephemeral.** All BGP state is in-process memory. On restart, sessions and paths must be re-established from CRD state; controller-runtime's reconcile loop handles this automatically.
- **EVPN Type 5 is implemented, not deferred.** `internal/runtime/gobgp/paths.go`'s `buildEVPNPaths` builds real `EVPNIPPrefixRoute` NLRIs, deriving the Route Distinguisher from `routerID + ":0"` (not from the CRD). The `BGPVRFInstance` CRD carries its own explicit `RouteDistinguisher` and import/export Route Targets (see Key Design Decisions above), applied via `internal/runtime/gobgp/runtime.go`'s `applyVRFs`. There is no `ErrMissingRouteDistinguisher` or similar rejection path in the current code.
- **No binary's `cmdDel` tears down shared kernel/CRD state.** See [ARCHITECTURE-CNI.md#known-constraints](../cni/architecture.md#known-constraints) for the CNI-side half; this reconciler's GC controller (`internal/gc`) is the asynchronous cleanup path for all of it.
