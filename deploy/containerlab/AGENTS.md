# ContainerLab Deployment — Galactic VPC Lab

## Important Conventions

- **YAML extensions**: Always use `.yaml`, never `.yml`.
- **fabric-router image**: `containers/fabric-router/Dockerfile` layers `tcpdump`, `mtr-tiny`, `telnet`, `dnsutils`, and `curl` onto the upstream `quay.io/frrouting/frr` image (version pinned via the Taskfile's `FRR_VERSION`, currently `10.2.0`). Built and tagged `fabric-router:latest` by `task build:fabric-router`, then used by the fabric DaemonSet (`resources/fabric-router/base/` builds on `config/fabric-router/` — see the "Shared manifests" bullet below — loaded into the Kind clusters via `deploy:images`) and the transit routers (`gvpc.clab.yaml`'s `kinds.linux.image`, picked up directly from the local Docker image cache). All reference sites set/require `imagePullPolicy: Never` where applicable — there's no registry to pull `fabric-router:latest` from. The image also bakes in the two files common to every fabric role, `containers/fabric-router/{daemons,vtysh.conf}`, to `/etc/frr-defaults/` (not `/etc/frr` directly, since that's an `emptyDir` populated at pod start), plus `fabric-config-agent` (`cmd/fabric-config-agent`), which the DaemonSet runs twice: as the `frr-init` init container it seeds `/etc/frr` from `/etc/frr-defaults/` and installs the node's own `frr.conf` from its `fabric-router.<nodename>` ConfigMap (read from the API by the pod's `NODE_NAME`, since a DaemonSet's `nodeAffinity` can match more than one node and BGP underlay config differs per node), and as the `config-agent` sidecar it applies later edits to that ConfigMap live with `frr-reload.py`. Every worker in every cluster carries `fabric: router`, so each site's `kustomization.yaml` generates one `fabric-router.<nodename>` ConfigMap per worker it has, each from that node's `frr.conf.<nodename>` file (mapped to key `frr.conf`), with `disableNameSuffixHash` so the names match what the agent looks up: dfw three (`frr.conf.dfw-worker`, `-worker2`, `-worker3`), sjc two, iad three (`frr.conf.iad-worker`, `-worker2`, `-worker3`) — no raw manifests remain under `resources/fabric-router/`. To change one node's underlay config on a running lab, edit its file and re-run `task deploy:fabric`: only that node's ConfigMap changes, and its sidecar reloads it in place (`kubectl -n galactic-system get events --field-selector involvedObject.name=fabric-router.<nodename>` shows `Applied` or `Rejected`).
- **Dual-stack transport**: the transit underlay carries both families. Every transit link has a numbered IPv6 `/64` and IPv4 `/24`, every node has an IPv6 `/128` and IPv4 `/32` loopback (the IPv4 one deliberately equal to that node's `bgp router-id`), and each link runs **two** BGP sessions — the existing IPv6 one plus a numbered IPv4 one — rather than one multiprotocol session with extended next-hop (RFC 8950). The IPv4 address family carries per-node `/32` loopbacks only: there is no IPv4 SRv6 locator, tenant IPv4 (`ns20`/`ns40`) rides inside SRv6 encapsulation, and link subnets are never redistributed, so any IPv4 underlay ping must be sourced from a loopback (`task verify:underlay`). `install.sh` opens TCP/179 on both `iptables` and `ip6tables` for this reason; Cilium runs with `ipv4.enabled=false`, so these addresses are invisible to the cluster network. Validate any `frr.conf` change with `vtysh -C -f <file>` inside `fabric-router:latest` before deploying (copy `vtysh.conf`/`daemons` into `/etc/frr` first — the image keeps its defaults in `/etc/frr-defaults/`). Every transit config enforces an IPv6 inbound prefix guardrail, `FILTER_PREFIX`/`MIN48` (`ipv6 prefix-list MIN48 seq 5 permit ::/0 le 47`): it drops anything broader than `/48` and permits `/48` and more specific — the site aggregates and host routes the fabric originates. Its IPv4 counterpart `MIN24`/`FILTER_PREFIX_V4` (`permit 0.0.0.0/0 le 23`) does the same at `/24`.
- **Image loading**: Uses `ctr --namespace k8s.io images import` (not `kind load docker-image`) due to containerd v2 incompatibility.
- **Only edge nodes face the transit**: the edge nodes (`dfw-worker2`, `dfw-worker3`, `sjc-worker2`, `iad-worker2`) are the sole transit-facing nodes and hold the only eBGP sessions to AS 65100 — one per node, on its own `bond0` uplink to its site's transit router. Every other worker sits *behind* its site's edge node(s) on site-internal links and reaches the fabric over iBGP: `dfw-worker`→`dfw-worker2`, `sjc-worker`→`sjc-worker2`, `iad-worker`→`iad-worker2`, and `iad-worker3`→`iad-worker2`. A compute node or the route reflector has no link to a transit router and no eBGP session anywhere. On those iBGP sessions the edge node sets `next-hop-self force` (a path it learned from the transit carries the transit router's own address as next hop, which the node behind it cannot reach; `force` is required because plain `next-hop-self` is not applied to *reflected* paths — a reflector preserves the originator's NEXT_HOP by design, RFC 4456 §10, and without it iad-worker's EVPN session sits in Active forever) and `route-reflector-client` (iBGP split horizon would otherwise stop it passing one client's prefixes to another — iad has two behind it). **`dfw-worker` is dual-homed** to both of dfw's edge nodes, one bond to each, and the two are equal ECMP paths — see the README's BGP design. This is a separate layer from galactic-router's EVPN mesh, which still terminates on `iad-worker3` for every node in the lab.
- **Bonded links**: every datapath-carrying link (each edge node's transit uplink, each compute node's uplink to its edge node) is a two-member 802.3ad bond, built on both ends by `group_files/common/mkbond.sh` — from `gvpc.clab.yaml`'s `exec` on the Kind nodes (baked into the `kindest-node-galactic` image) and from `node_files/tr*/startup.sh` on the transit routers (bind-mounted). Addresses, FRR `interface` stanzas and every datapath env var (`GALACTIC_GATEWAY_{PUBLIC,INTERNAL}_INTERFACE(S)`, `GALACTIC_NAT_UPLINK_INTERFACES`, `GALACTIC_CNI_EBPF_INTERFACES`) name the bond, never a member. Kind-node bond names are uniform per role — `bond0` the first uplink, `bond1` an edge node's compute-facing link or `dfw-worker`'s second uplink — so one cluster-wide `galactic-cni` value fits every node in a site. Adding or moving a bonded link means keeping four places in step: `gvpc.clab.yaml` (links + exec), `node_files/tr*/startup.sh`, `Taskfile.yaml`'s `deploy:lab-xdp-passthrough` port list (transit-side *members*), and `scripts/verify-bonds.sh`/`verify-bond-failover.sh`. See the README's "Bonded links" section for the member table.
- **No node renaming**: Kind's own sequential worker names (`<cluster>-worker`, `-worker2`, `-worker3`) are used verbatim everywhere — container name, Kubernetes node name, `fabric-router.<nodename>` ConfigMap name, `targetRef`, and `kubernetes.io/hostname` pin all agree by construction. There is no `kubeadmConfigPatches` hostname rewrite and no post-deploy `docker rename` step; a node's role is carried entirely by its labels. An earlier version of this lab renamed `iad-worker2`→`iad-worker-rr` and `iad-worker3/4`→`iad-gateway1/2`, which meant every one of those references had to be kept in sync by hand.
- **iad-worker3 (the EVPN route reflector)**: the single reflector for all three clusters — every galactic-router in dfw, sjc and iad is a client of it (`fc00:0:8::1`, port 1790), and compute and edge nodes therefore never peer with each other directly in the overlay. Underlay-wise it is an ordinary node behind `iad-worker2` like any compute node, with one iBGP session and no transit uplink. It needs a worker of its own: `galactic=control` and `galactic=router` are two values of one label key, so a reflector can't also be a compute or edge node (it would lose `galactic-cni`), and `config/galactic-router/overlays/control/` excludes Kubernetes control-plane nodes outright.
- **galactic-router image**: Uses `galactic-router:latest` with `imagePullPolicy: Never` — stale images persist across rebuilds.
- **Kind serviceSubnet**: All clusters use `/108` service subnet (non-standard; may cause issues with some services).
- **BGP listen port**: Compute worker DaemonSets run with `GALACTIC_ROUTER_BGP_LISTEN_PORT=-1` (outbound-only). The RR role listens on `1790` (set in `config/galactic-router/overlays/control/daemonset-patch.yaml`).
- **BGP remote port**: BGPPeer CRDs inside `resources/galactic-router/{dfw,iad,sjc}/` explicitly set `remotePort: 1790` to connect to the RR. The control/RR-side peers in `resources/galactic-control/iad/` rely on galactic-router's default of `1790`.
- **Worker SRv6 blackhole route**: A single standalone blackhole route covering the node's `/64` uSID space — its `/48` Block plus its own Node-ID, which is the width `internal/plumbing/ebpf/uformat.go`'s `LocatorBits = BlockBits + NodeIDBits` (64 bits) gives a node, so it covers exactly the SIDs that node can issue (`metric 2048`, no interface — `ip -6 route add blackhole` takes no `dev`) prevents the default route from matching any USID this node could compute, set via `exec` commands in the ContainerLab topology. One aggregate route rather than one per VPC: IPv6 FIB lookup is longest-prefix-match first, so a real seg6local `/128` decap route always wins over the covering blackhole regardless of metric — the aggregate protects every current and future VPC's SID with no per-VPC config needed. The USID is **not** configured as an address on any interface. The seg6local route (`metric 1024`) in the main table handles SRv6 decapsulation. If the USID were an interface address, the kernel's local table route (metric 0) would shadow the seg6local route and break decapsulation. (A dedicated `lo-galactic` dummy interface previously hosted this — removed since it wasn't referenced by any Go code or by the blackhole route itself; `install.sh`'s `all`/`default` sysctl entries already cover the SRv6 kernel knobs it existed for.)
- **Node labels**: this lab follows the same label strategy as production (see the root `AGENTS.md`'s "Node label strategy" table) — a primary-role enum (`node`) plus a mode enum per binary family (`galactic`, `fabric`), not one giant enum or a pile of independent booleans:
  - `galactic.datumapis.com/node: compute` — one per site (`dfw-worker`, `sjc-worker`, `iad-worker`); deploys nothing keyed on this label itself since `galactic-nat` moved to the edge nodes. Each compute node egresses only through its own site's edge shards (`resources/galactic-cni/<site>/egress-shards-patch.yaml`).
  - `galactic.datumapis.com/node: edge` — `dfw-worker2`, `dfw-worker3`, `sjc-worker2`, `iad-worker2`; deploys `galactic-gateway` (standalone, single-container, one pinned DaemonSet per node since `GALACTIC_GATEWAY_SRV6_ADDRESS` is per-node) and `galactic-nat` (one DaemonSet per site, identity from each node's `EgressShard`), so all four double as this lab's egress shards — dfw has two. The shard runs chained behind the gateway's XDP programs (`GALACTIC_NAT_XDP_ATTACH=chain`). dfw has the only pair, so it is the site that exercises active-active anycast. Each edge node carries a matching `NoSchedule` taint.
  - `galactic.datumapis.com/galactic: router` — every `compute` *and* every `edge` node (seven in all); deploys `galactic-cni` and plain-mode `galactic-router` together. Mutually exclusive with `galactic: control` below (one label key, one value).
  - `galactic.datumapis.com/galactic: control` — `iad-worker3` only; deploys `galactic-router-rr`. Not a `galactic.datumapis.com/node` value — a matching `NoSchedule` taint uses the same key/value.
  - `galactic.datumapis.com/fabric: router` — every worker in the lab (all eight); deploys `fabric-router`, independently of whatever other labels a node carries. Note this is *not* the same as being transit-facing: every worker runs FRR, but only the edge nodes' FRR holds an eBGP session to the transit; the rest run iBGP to their site's edge node.
  - **`remote-host`** carries none of these and is in no cluster at all: a plain nginx container on `tr4` (`containers/remote-host/Dockerfile`, `node_files/remote-host/startup.sh`) that configures its own dual-stack transit link statically and speaks no BGP. `tr4` originates its `2001:db8:1:40::/64` and `10.1.40.0/24` on its behalf. It exists so tenant egress through the NAT egress tier has a real off-fabric destination, and so an edge gateway's ingress VIP has a real off-fabric client.
  - See `node_files/{dfw,iad,sjc}/config.yaml` for the actual assignments, and `config/galactic-router/overlays/control/daemonset-patch.yaml` / `config/galactic-nat/base/daemonset.yaml` for the full reasoning behind each split.
- **GC namespace**: The default-role DaemonSet sets `GALACTIC_ROUTER_GC_NAMESPACE=galactic-system` for namespace-scoped garbage collection.
- **FRR config**: Transit router configs omit the `frr version` directive (managed by the FRR image, not the config).
- **Shared manifests**: `resources/galactic-cni/kustomization.yaml` builds on `config/galactic-cni/`, `resources/galactic-router/base/kustomization.yaml` builds on `config/galactic-router/overlays/router/`, `resources/galactic-control/iad/kustomization.yaml` builds on `config/galactic-router/overlays/control/`, and `resources/fabric-router/base/kustomization.yaml` builds on `config/fabric-router/` (each in turn pulls in its own `base/` where one exists: `config/galactic-router/base/`; `config/fabric-router/` has no role split, it's a single flat DaemonSet) rather than forking them, patching in only what the lab needs to differ (image, env — for fabric, just `image: fabric-router:latest` + `imagePullPolicy: Never` on all three containers via `fabric-lab-patch.yaml`, which overrides nothing else). `config/fabric-router/`'s own affinity already covers every fabric-needing node via `galactic.datumapis.com/fabric: router` (every lab worker carries it, regardless of its other labels), so the lab inherits it as-is: one fabric DaemonSet per cluster, one `fabric-router.<nodename>` ConfigMap per matching node. (A second overlay, `resources/fabric-control/iad/`, used to exist purely so the reflector node could get its own `frr.conf` back when the DaemonSet read a single shared `frr.conf` — it narrowed the base affinity to `node: [compute, edge]`, narrowed its own to `galactic: control`, and needed a JSON6902 `/metadata/name` rename to `fabric-control` to avoid clobbering the base DaemonSet in the same namespace. Per-node config selection removed the need for all three, and it was deleted; the reflector node is now served by the single DaemonSet like every other node. It was never the underlay's route reflector — that's `fabric-router-rr` on `fabric=control`, still unimplemented, see `docs/node-labels.md`.) `kubectl apply -k` refuses to load resource files from outside a kustomization's own root, so `deploy-cni.sh`/`deploy-galactic-router.sh`/`deploy-fabric.sh` `docker cp` those directories into a local `base/` subdirectory on the node at deploy time (`resources/galactic-cni/base/`, `resources/galactic-router/base/{base,overlays/router}/`, `resources/galactic-control/iad/{base,overlays/control}/` — each nested at the same relative depth as `config/galactic-router/` itself, since the copied `overlays/router`/`overlays/control` kustomization.yamls' own `../../base` references are copied verbatim, `resources/fabric-router/base/fabric/`) instead of referencing `config/` across that boundary. The `galactic-system` namespace and RBAC/ServiceAccount are applied straight from `config/galactic-system/namespace.yaml` and `config/*/{rbac,serviceaccount}.yaml` by `deploy-system.sh` via `lib.sh`'s `copy_config` (which copies all of `config/` to `/galactic/config/`) — not part of any kustomize build, so per-site `namePrefix` never touches the shared cluster-scoped RBAC. `config/galactic-system/namespace.yaml` is also the only place `galactic-system` gets created for production — there is no other bootstrap step in this repo, so if it's ever missing on a real cluster, deploying `config/galactic-router/` or `config/galactic-cni/` fails outright.

## Naming Layers

- **Fabric** — FRR DaemonSets running on each cluster's workers; handle eBGP to the transit mesh. Resources live in `resources/fabric-router/`.
- **Galactic Router** — galactic-router DaemonSets running on each cluster's workers; handle iBGP EVPN route distribution. Resources live in `resources/galactic-router/`.
- **Control** — the route-reflector node's resources (`resources/galactic-control/iad/`); its FRR fabric comes from the same `resources/fabric-router/iad/` DaemonSet as every other iad node.
- **iad-control** — `iad-worker3`, the lab's single EVPN route reflector; every galactic-router in every cluster peers with it. galactic-router + BGP CRDs in `resources/galactic-control/iad/` (one `bgppeer-<nodename>.yaml` per client), fabric in `resources/fabric-router/iad/` (`frr.conf.iad-worker3`).
- **Edge** — the four `node=edge` workers running `galactic-gateway`'s XDP DSR/Maglev datapath. One overlay per node under `resources/galactic-gateway/<nodename>/` (DaemonSet patch + BGPRouter + BGPPeer + NetworkGateway), plus one per-site entry point `resources/galactic-gateway/<site>/` carrying that site's `NetworkRule`/`ServiceVIPBinding`. All three sites share one anycast VIP (`2001:db8:6060::1`) with site-local `ns60` backends.
- **Egress** — `galactic-nat`, one egress shard per edge node, chained behind that node's gateway. One per-site overlay under `resources/galactic-nat/<site>/` (uplink override + one `EgressShard` per edge node; dfw has two). Each site's compute node lists only its own site's shard SIDs (`resources/galactic-cni/<site>/egress-shards-patch.yaml`), and each edge node's `frr.conf` originates its shard's SID `/64` and masquerade addresses.
